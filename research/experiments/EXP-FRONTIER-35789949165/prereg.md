## 2. State, action, target, unit of analysis

**State representation (raw -> derived, no BrowserGym required):**
- Raw (synthetic orthogonal+mixed): `url` string as observed, `method` (GET/POST), synthetic `headers_observed`/`body_observed` dicts (for mixed, both headers_observed and body_observed and url_query contain aliased keys simultaneously within one request). Plus `intent` string (goal).
- Derived for retrieval/mining and reconstruction/invocation: `url_path` (split `/`), `url_query` dict (parse `?k=v`), `url_segments` list, `header_keys_observed` (lowercased keys from headers_observed), `body_json_keys` (parsed JSON keys if applicable), serialized query string `intent + ' ' + url_path + ' ' + query_keys + ' ' + header_keys + ' ' + body_keys + ' ' + method` for centroid scoring. Losses disclosed: visual layout pixels, timing, auth token values beyond key presence, AX tree — bounded to tested header/body/auth aliasing + mixed.
- Hierarchical component representation: For each mechanism episode, parse `action_template` string to extract semantic components: `url_segments` (non-slot path tokens), `query_keys` (keys before `=` or `${slot}`), `header_keys` (e.g., `ApiKey`, `X-Reset-Token`), `body_fields` (JSON keys), `auth_scopes` (permission values). Extract via regex `\$\{[^}]+\}` for slots and string splitting, no hidden_expected access. Components are sets; themes are clusters of episodes by Jaccard(component_set_i, component_set_j) >=0.6.
- WebAPI endpoint representation: For each endpoint spec (method + path_template + header_template + body_template + auth_scope), parse similarly to extract endpoint components: `path_segments`, `query_keys`, `header_keys`, `body_fields`, `auth_scopes`, `method`. Endpoint themes are clusters of endpoint specs by Jaccard(endpoint_component_set_i, endpoint_component_set_j) >=0.6. AX fields None for synthetic; no 1280x720 viewport needed per Director rationale.
- Forbidden: `alias_family`, `query_key`, `target_prefix`, `routing_prefix`, `target_style`, `path_style`, `header_key`, `body_field`, `auth_scope`, `expected_template`, `expected_endpoint`, `resource` answer labels are NOT in derived_context nor in component/endpoint extraction; stored only as hidden `expected` metadata for scoring. Audit verifies no forbidden reads via harness `hierarchical_retrieve`/`flat_retrieve`/`webapi_mine` signatures and index manifest audit.

**Action/endpoint representation:**
- Mechanism `action_template` is URL/header/body/auth template strings with `${slot}` (e.g., `/users/${id}`, `ApiKey: ${token}` vs `X-Reset-Token: ${token}`, `{"apiKey":"${token}"}` vs `{"key":"${token}"}`, `scope:${perm}`) and for mixed tasks simultaneously header+body+query slots. Endpoint spec is tuple (method, path_template, header_template, body_template, auth_scope) with same slot syntax. Binding via deterministic `kernel._bind` plus header/body field substitution. Retrieval returns candidate set (k=5 flat, adaptive 2-5 hierarchical, 3-5 endpoint mining complementarily across themes). Reconstruction/invocation after retrieval/mining may score each candidate template/endpoint's structural match to derived state and rewrite via `adopt-any-observed-key-not-in-registry + rewrite_template_multi` (alphabetically-sorted multi-adoption) or endpoint_choose_adoptions before `_bind`, conditioned only on `(intent, derived_context, candidates)`. Confidence derived from candidate endpoint-relevance softmax over candidates (temp 0.15) + deterministic jitter gated UNKNOWN<0.80 for ECE; hierarchical/WebAPI retrieval scoring is theme-centroid cosine (TFIDF or embed) not hardcoded. No hidden_expected access.

**Target (primary measurand):**
- Per-task outcome in `{correct_resolution, correct_endpoint_invocation, false_accept, UNKNOWN}` (mutually exclusive per pipeline, sum to 1 per stratum).
  - `correct_resolution` (template pipelines) = retrieval set contains rewritable candidate and reconstruction selects/rewrites to alias-correct template with `bound_action` (url+header+body jointly for mixed) equals `expected_bound` (hidden_expected_template bound).
  - `correct_endpoint_invocation` (WebAPI) = mined endpoint candidate set contains endpoint that after deterministic binding yields `expected_endpoint_bound` (method+path+header+body+auth jointly correct).
  - `false_accept` = resolved/invoked to wrong template/endpoint or bound incorrectly or should have abstained.
  - `UNKNOWN` = correctly abstains when no applicable mechanism/endpoint or gated confidence<0.80.
- Retrieval/endpoint measurands per task:
  - `recall@k` = 1 if candidate set contains at least one mechanism/endpoint whose template after genuine reconstruction/invocation yields correct bound, else 0. Coverage = mean recall@k over pooled.
  - `distinct_components` = number of distinct semantic/endpoint component types (header vs body vs auth vs path segments) represented in candidate set; density = distinct_components / k.
  - Coverage gain = WebAPI coverage - best flat coverage (max of TFIDF-K5 and EMBED-K5) and hierarchical coverage - best flat coverage reported separately. Evidence density gain = WebAPI density - best flat density.
- Secondary: calibration — `ECE` over 5 confidence bins (candidate-relevance-derived confidence), abstention precision/recall; per-family (header/body/auth) and held-out-9 and mixed-10 breakdowns; adaptive k distribution; endpoint theme count.
- Mixed multi-channel target: correct only if ALL channels (header + body + query + method) jointly correctly rewritten/invoked; partial counts as false_accept.

**Unit of analysis:** Single `retrieve(k) + reconstruct_resolve + bind` or `mine(k) + endpoint_invoke + bind` call per task. Paired design: each task evaluated under each pipeline (within-task). Resampling unit is task family (block bootstrap over tasks grouped by family header/body/auth/mixed to respect trajectory-grouped structure per Director question).
