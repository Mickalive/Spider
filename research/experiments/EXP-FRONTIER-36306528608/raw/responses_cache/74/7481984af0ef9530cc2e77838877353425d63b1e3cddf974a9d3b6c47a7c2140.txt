While we aim to make this as smooth as possible, there are still the general complexities based on your design. With this approach, you can employ strategies such as <a href=/administration/backup_restore/backup_gitlab/#configuring-cron-to-make-daily-backups>automated backups</a> for recovery. These strategies provide a good level of recovery time objective (RTO) or recovery point objective (RPO) while avoiding the complexities that come with HA.</p><p>With standalone setups, especially single node environments, various options are available for <a href=/install/>installation</a> and management. The options include <a href=https://page.gitlab.com/cloud-partner-marketplaces.html>the ability to deploy directly by using select cloud provider marketplaces</a> that reduce the complexity a little further.</p><h3 id=high-availability-ha>High Availability (HA)</h3><p>High Availability ensures every component in the GitLab setup can handle failures through various mechanisms. However, to achieve this is complex, and the environments required can be sizable.</p><p>For environments serving 3,000 or more users, we generally recommend using an HA strategy. At this level, outages have a bigger impact on more users. All the architectures in this range have HA built in by design for this reason.</p><h4 id=do-you-need-high-availability-ha>Do you need High Availability (HA)?</h4><p>As mentioned previously, achieving HA comes at a cost. The environment requirements are sizable as each component needs to be multiplied, which comes with additional actual and maintenance costs.</p><p>For a lot of our customers with fewer than 3,000 users, we&rsquo;ve found that a backup strategy is sufficient and even preferable. While this does have a slower recovery time, it also means you have a much smaller architecture and less maintenance costs as a result.</p><p>As a general guideline, employ HA only in the following scenarios:</p><ul><li>When you have 3,000 or more users.</li><li>When GitLab being down would critically impact your workflow.</li></ul><h4 id=scaled-down-high-availability-ha-approach>Scaled-down High Availability (HA) approach</h4><p>If you still need HA for fewer users, you can achieve it with an adjusted <a href=/administration/reference_architectures/3k_users/#supported-modifications-for-lower-user-counts-ha>3K architecture</a>.</p><h4 id=zero-downtime-upgrades>Zero-downtime upgrades</h4><p><a href=/update/zero_downtime/>Zero-downtime upgrades</a> are available:</p><ul><li>For standard environments with HA.</li><li>In GitLab 18.9 and later, also for Cloud Native Hybrid environments.</li></ul><p>Zero-downtime upgrades allow for an environment to stay up during an upgrade. However, this process is
more complex as a result and has some limitations that detailed in the documentation.</p><p>When going through this process, it&rsquo;s worth noting that there may still be brief moments of downtime when the HA mechanisms take effect.</p><p>In most cases, the downtime required for doing an upgrade shouldn&rsquo;t be substantial. Use this approach only if it&rsquo;s a key requirement for you.</p><h3 id=gitlab-geo-cross-regional-distribution--disaster-recovery>GitLab Geo (Cross Regional Distribution / Disaster Recovery)</h3><p>With <a href=/administration/geo/>GitLab Geo</a>, you can achieve distributed environments in
different regions with a full Disaster Recovery (DR) setup in place. GitLab Geo
requires at least two separate environments:</p><ul><li>One primary site.</li><li>One or more secondary sites that serve as replicas.</li></ul><p>If the primary site becomes unavailable, you can fail over to one of the secondary sites.</p><div class="alert alert-type-note gl-rounded-lg"><div class=alert-icon></div><div class=gl-min-w-0><p>Use this advanced and complex setup only if DR is
a key requirement for your environment. You must also make additional decisions
on how each site is configured. For example, if each secondary site would be the
same architecture as the primary or if each site is configured for HA.</p></div></div><h3 id=large-monorepos--additional-workloads>Large monorepos / Additional workloads</h3><p><a href=/install/sizing/#large-monorepos>Large monorepos</a> or significant <a href=/administration/reference_architectures/#additional-workloads>additional workloads</a> can affect the performance of the environment notably. Some adjustments may be required depending on the context.</p><p>For comprehensive analysis of these factors, see <a href=/install/sizing/>reference architecture sizing</a>, which provides:</p><ul><li>Detailed assessment methodology for monorepo impacts on infrastructure.</li><li>Component-specific scaling recommendations for different workload patterns.</li><li>Network bandwidth analysis for heavy data transfer scenarios.</li></ul><p>If this situation applies to you, reach out to your GitLab representative or our <a href=https://about.gitlab.com/support/>Support team</a>

<a href=/install/cloud-services/>cloud services for GitLab components</a>.</p><h2 id=deviating-from-the-suggested-reference-architectures>Deviating from the suggested reference architectures</h2><p>The further away you move from the reference architectures,
the harder it is to get support. With each deviation, you introduce
a layer of complexity that complicates troubleshooting potential
issues.</p><p>These architectures use the official Linux packages or <a href=https://docs.gitlab.com/charts/>Helm Charts</a> to
install and configure the various components. The components are
installed on separate machines (virtualized or Bare Metal). Machine hardware
requirements are listed in the &ldquo;Configuration&rdquo; columns on specific reference architecture pages. Equivalent VM standard sizes are listed
in the GCP/AWS/Azure columns of each <a href=/administration/reference_architectures/#available-reference-architectures>available architecture</a>.</p><p>You can run GitLab components on Docker, including Docker Compose. However, it is still an additional layer and might add some support complexities. For example, not being able to run <code>strace</code> in containers.</p><h3 id=unsupported-designs>Unsupported designs</h3><p>While we try to have a good range of support for GitLab environment designs, certain approaches don&rsquo;t work effectively. The following sections detail these unsupported approaches.</p><h4 id=stateful-components-in-kubernetes>Stateful components in Kubernetes</h4><p><a href=https://docs.gitlab.com/charts/installation/#configure-the-helm-chart-to-use-external-stateful-data>Running stateful components in Kubernetes, such as Postgres and Redis, is not supported</a>.</p><p>You can use other supported cloud provider services, unless specifically called out as unsupported.</p><p>Individual Gitaly nodes can be deployed on Kubernetes and are generally available. This provides a non-HA solution where each repository is stored on a single node. For context on Gitaly deployment options and limitations, see <a href=/administration/gitaly/kubernetes/#context>Gitaly on Kubernetes</a>.</p><p>For reference architectures that deploy Gitaly in Kubernetes as part of a fully cloud-native setup, see <a href=/administration/reference_architectures/cloud_native/>Cloud Native reference architectures</a>.</p><h4 id=deploying-one-environment-over-multiple-regions>Deploying one environment over multiple regions</h4><p>GitLab does not support deploying a single environment across multiple regions. These setups can result in significant issues, such as excessive network latency or split-brain scenarios if connectivity between regions fails.</p><p>Several GitLab components perform synchronous replication or require an odd number of nodes to function correctly, such as Consul, Redis Sentinel, and Praefect. Distributing these components across multiple regions with high latency can severely impact their functionality and the overall system performance.</p><p>This limitation applies to all potential GitLab environment setups, including Cloud Native Hybrid alternatives.</p><p>For deploying GitLab over multiple data centers or regions, we offer <a href=/administration/geo/>GitLab Geo</a> as a comprehensive solution.</p><h2 id=how-specifications-are-derived>How specifications are derived</h2><p>Specifications are informed by real customer data and ad-hoc performance testing.</p><h3 id=how-we-perform-the-tests>How we perform the tests</h3><p>Testing is conducted using specific coded workloads derived from sample customer data, utilizing both the <a href=https://gitlab.com/gitlab-org/gitlab-environment-toolkit>GitLab Environment Toolkit (GET)</a> for environment deployment with Terraform and Ansible, and the <a href=https://gitlab.com/gitlab-org/quality/performance>GitLab Performance Tool (GPT)</a> for performance testing with k6.</p><p>Testing is performed primarily on GCP and AWS using their standard compute offerings (n1 series for GCP, m5 series for AWS) as baseline configurations. These machine types were selected as a lowest common denominator target to ensure broad compatibility. Specifications are calibrated on standard general-purpose x86 compute - any machine type meeting or exceeding the vCPU and memory requirements is expected to work, including newer CPU generations and ARM-based instances. The architectures are expected to perform similarly on any hardware meeting the specifications, whether on other cloud providers or on-premises.</p><h3 id=performance-targets>Performance targets</h3><p>Each reference architecture is tested against specific throughput targets based on real customer data. For every 1,000 users, we test:</p><ul><li>API: 20 RPS</li><li>Web: 2 RPS</li><li>Git (Pull): 2 RPS</li><li>Git (Push): 0.4 RPS (rounded to the nearest integer)</li></ul><p>The listed RPS targets were selected based on real customer data of total environmental loads corresponding to the user count, including CI and other workloads.</p><div class="alert alert-type-note gl-rounded-lg"><div class=alert-icon></div><div class=gl-min-w-0><ul><li>These RPS breakdowns represent test targets based on typical workload patterns. Your actual workload composition may
vary. For guidance on assessing your specific RPS composition and when adjustments are needed, see
<a href=/install/sizing/#understanding-rps-composition-and-workload-patterns>Understanding RPS composition</a>.</li><li>Network latency between components in test environments was observed at &lt;5 ms but note this is not intended as a hard requirement.</li></ul></div></div><h3 id=test-coverage-and-results>Test coverage and results</h3><p>Testing is designed to be effective and provide good coverage for the reference architecture targets, spanning Linux package and Cloud Native environments. The specific environments and configurations tested are reviewed regularly to ensure the best coverage and cost-to-value balance, and may change over time.</p><p>Our testing also includes prototype variations of these architectures being explored for potential future inclusion. Test results are publicly available on the <a href=https://gitlab.com/gitlab-org/reference-architectures/-/wikis/Benchmarks/Latest>Reference Architecture wiki</a>.</p><h2 id=maintaining-a-reference-architecture-environment>Maintaining a reference architecture environment</h2><p>Maintaining a reference architecture environment is generally the same as any other GitLab environment.</p><p>In this section you can find links to documentation for relevant areas and specific architecture notes.</p><h3 id=scaling-an-environment>Scaling an environment</h3><p>The reference architectures are designed as validated starting points based on typical workload patterns, not final configurations. Most production deployments benefit from adjustments based on actual usage patterns that emerge through monitoring. The architectures are scalable throughout, and you can tune them iteratively as your workload characteristics become clear. Scaling can be done component-by-component or wholesale to the next architecture size when metrics indicate sustained resource pressure.</p><div class="alert alert-type-note gl-rounded-lg"><div class=alert-icon></div><div class=gl-min-w-0><p>If a component is continuously exhausting its given resources, reach out to our <a href=https://about.gitlab.com/support/>Support team</a> before performing any significant scaling.</p></div></div><h4 id=when-to-scale>When to scale</h4><p>Most deployments benefit from adjustments after observing actual workload patterns. Common scenarios that trigger scaling include:</p><p><strong>Resource sizing adjustments:</strong></p><ul><li>Increasing Webservice/Rails capacity for API-heavy workloads, particularly when API traffic exceeds 90% of total RPS (see <a href=/install/sizing/#understanding-rps-composition-and-workload-patterns>Understanding RPS composition</a>)</li><li>Scaling Gitaly for monorepo-heavy environments or when repository sizes exceed 2 GB (see <a href=/install/sizing/#identify-component-adjustments>Identify component adjustments</a>)</li><li>Adjusting Sidekiq workers for high CI/CD throughput or heavy background job processing</li></ul><p><strong>Configuration tuning:</strong></p><ul><li>Setting Gitaly repository cgroup counts based on concurrent access patterns (see <a href=/administration/gitaly/cgroups/>Gitaly cgroups</a>)</li><li>Configuring Sidekiq queue priorities for job processing optimization (see <a href=/administration/sidekiq/processing_specific_job_classes/>processing specific job classes</a>)</li></ul><p><strong>Architecture refinements:</strong></p><ul><li>Adding PostgreSQL read replicas for read-heavy workloads</li><li>Splitting Sidekiq into specialized pools for different job types</li><li>Adjusting minimum instance counts for environments with sharp traffic spikes</li></ul><p>These adjustments are typical and expected. Reference architectures provide the foundation, but monitoring your specific workload determines the optimal configuration. For systematic assessment of your environment, see <a href=/install/sizing/>reference architecture sizing</a>.</p><h4 id=scaling-for-gitlab-duo-agent-platform>Scaling for GitLab Duo Agent Platform</h4><p>GitLab Duo Agent Platform introduces additional infrastructure requirements beyond standard GitLab workloads. Agent Platform workflows execute through the GitLab Rails API, process jobs asynchronously through Sidekiq, and access repository data for code context and analysis.</p><p>Agent Platform usage scales with automation and agent activity, not user count, so it doesn&rsquo;t
follow the traffic patterns the reference architecture RPS targets are based on. An environment
sized correctly for its user count can still come under sustained resource pressure from
agentic workloads. Monitor the components below directly rather than assuming standard sizing
accounts for Agent Platform usage.</p><p>Primary component impacts:</p><ul><li><strong>Rails (Webservice/Puma)</strong> - Agent Platform API requests add to overall request load and WebSocket connections for streaming AI responses are managed by Workhorse</li><li><strong>Sidekiq</strong> - AI completion jobs and workflow state updates are processed as background jobs</li><li><strong>PostgreSQL</strong> - Agent workflow sessions and state data are stored in the database</li><li><strong>Gitaly</strong> - Repository file access for code context and commit operations for agent-generated changes</li></ul><p>For environments planning Agent Platform adoption:</p><ul><li>Deploy the recommended architecture size based on your standard workload RPS</li><li>Monitor Rails CPU utilization during initial rollout</li><li>Monitor Sidekiq CPU utilization and job queue depths</li><li>Monitor PostgreSQL for increased transaction rates from workflow state management</li><li>Monitor Gitaly for increased file access patterns from code analysis features</li></ul><p>For example Prometheus queries to monitor these components, see <a href=/administration/monitoring/prometheus/#sample-prometheus-queries>sample Prometheus queries</a>.</p><p>If you observe sustained resource pressure, increase capacity by scaling the affected components. In Kubernetes deployments, increase pod replicas and node pool capacity. In Linux package deployments, scale horizontally by adding nodes or vertically by increasing node specifications.</p><p>Resource requirements vary based on Agent Platform usage intensity and specific features enabled. Treat the recommended architecture size as a starting point for Agent Platform adoption, not a guarantee of sufficient headroom, and scale based on observed metrics.</p><h4 id=how-to-scale>How to scale</h4><p>For most components, vertical and horizontal scaling can be applied as usual. However, before doing so, be aware of the following caveats:</p><ul><li>When scaling Puma or Sidekiq vertically, the amount of workers must be adjusted to use the additional specifications. Puma worker counts are typically adjusted automatically, but Sidekiq may require <a href=/administration/sidekiq/extra_sidekiq_processes/#start-multiple-processes>manual configuration</a>.</li><li>Redis and PgBouncer are primarily single threaded. If these components are seeing CPU exhaustion, they might have to be scaled out horizontally.</li><li>In Linux package deployments, the Consul, Redis Sentinel, and Praefect components require an odd number of nodes for a voting quorum when deployed in HA form.</li><li>Scaling certain components significantly can result in notable knock on effects that affect the performance of the environment. For more guidance, see <a href=/administration/reference_architectures/#scaling-knock-on-effects>Scaling knock on effects</a>.</li></ul><p>Conversely, if you have robust metrics in place that show the environment is over-provisioned, you can scale downwards.
You should take an iterative approach when scaling downwards, to ensure there are no issues.</p><h4 id=scaling-knock-on-effects>Scaling knock on effects</h4><p>In some cases, scaling a component significantly may result in knock on effects for downstream components, impacting performance. The architectures are designed with balance in mind to ensure components that depend on each other are congruent in terms of specifications. Notably scaling a component may result in additional throughput being passed to the other components it depends on. As a result, you could have to scale these other dependent components as well. To determine this, monitor the saturation metrics of all dependent services before scaling. If multiple interdependent components show saturation, they should be scaled together in a coordinated manner rather than sequentially, preventing bottlenecks from simply shifting between components.</p><div class="alert alert-type-note gl-rounded-lg"><div class=alert-icon></div><div class=gl-min-w-0><p>The architectures have been designed to have elasticity to accommodate an upstream component being scaled. However, reach out to our <a href=https://about.gitlab.com/support/>Support team</a> before you make any significant changes to your environment to be safe.</p></div></div><p>The following components can impact others when they have been significantly scaled:</p><ul><li>Puma and Sidekiq - Notable scale ups of either Puma or Sidekiq workers will result in higher concurrent connections to the internal load balancer, PostgreSQL (via PgBouncer if present), Gitaly (via Praefect if present) and Redis.<ul><li>Redis is primarily single-threaded. In some cases, you might have to split Redis into separate instances (for example, cache and persistent) if the increased throughput causes CPU exhaustion in a combined cluster.</li><li>PgBouncer is also single threaded but a scale out might result in a new pool being added that in turn might increase the total connections to Postgres. It&rsquo;s strongly recommended to only do this if you have experience in managing Postgres connections and to seek assistance if in doubt.</li></ul></li><li>Gitaly Cluster (Praefect)/PostgreSQL - A notable scale out of additional nodes can have a detrimental effect on the HA system and performance due to increased replication calls to the primary node.</li></ul><h4 id=scaling-from-a-non-ha-to-an-ha-architecture>Scaling from a non-HA to an HA architecture</h4><p>In most cases, vertical scaling is only required to increase an environment&rsquo;s resources. However, if you are moving to an HA environment,
additional steps are required for the following components to switch over to their HA forms.</p><p>For more information, see the following documentation:</p><ul><li><a href=/administration/redis/replication_and_failover/#switching-from-an-existing-single-machine-installation>Redis to multi-node Redis w/ Redis Sentinel</a></li><li><a href=/administration/postgresql/moving/>Postgres to multi-node Postgres w/ Consul + PgBouncer</a></li><li><a href=/administration/gitaly/praefect/#migrate-to-gitaly-cluster-praefect>Gitaly to Gitaly Cluster (Praefect)</a></li></ul><h3 id=upgrades>Upgrades</h3><p>Upgrading a reference architecture environment is the same as any other GitLab environment. For more information, see
<a href=/update/>upgrade GitLab</a>. <a href=/administration/reference_architectures/#zero-downtime-upgrades>Zero-downtime upgrades</a> are also available.</p><div class="alert alert-type-note gl-rounded-lg"><div class=alert-icon></div><div class=gl-min-w-0><p>You should upgrade a reference architecture in the same order as you created it.</p></div></div><h3 id=monitoring>Monitoring</h3><p>You can monitor your infrastructure and <a href=/administration/monitoring/>GitLab</a> using various options. See the selected monitoring solution&rsquo;s documentation for more information.</p><div class="alert alert-type-note gl-rounded-lg"><div class=alert-icon></div><div class=gl-min-w-0><p>GitLab application is bundled with <a href=/administration/monitoring/prometheus/>Prometheus and various Prometheus compatible exporters</a> that could be hooked into your solution.</p></div></div><h2 id=update-history>Update history</h2><p>You can find a full history of changes <a href="https://gitlab.com/gitlab-org/gitlab/-/merge_requests?scope=all&amp;state=merged&amp;label_name%5B%5D=Reference%20Architecture&amp;label_name%5B%5D=documentation">on the GitLab project</a>.</p></div><div data-vue-app=back-to-top-button></div></div><div class="feedback gl-min-h-8" data-ga-section=feedback data-elastic-exclude><div data-component=docs-feedback><div class="gl-mt-9 gl-min-h-8"><div class="gl-flex gl-justify-between gl-items-center"><div class="gl-flex gl-items-center feedback-form"><span class=gl-mr-5>Was this page helpful?</span>
