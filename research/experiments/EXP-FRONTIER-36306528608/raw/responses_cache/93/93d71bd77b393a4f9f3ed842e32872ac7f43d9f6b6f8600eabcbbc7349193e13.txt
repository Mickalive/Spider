        <article
            class="blog-body rounded-2xl border border-white/10 bg-white/[0.02] p-6 md:p-8 shadow-[0_20px_80px_rgba(0,0,0,0.45)]"
        >
            <p>Most AI coding agents that touch a REST API in their first session do something predictable: they generate code that fetches a resource, finds it returns 12 fixture users with shallow shapes, write a wrapper that assumes those shapes hold in production, and then break the moment the user points the agent at a real API.</p>
<p>The legacy <code>/api/users</code> endpoint at reqres.in is great for humans learning HTTP. It&#39;s the wrong shape for an agent practicing real code. So we built a new one.</p>
<p>Today we&#39;re launching the <strong>ReqRes Agent Sandbox</strong>: a set of endpoints under <code>/agent/v1/*</code> designed specifically for AI coding agents to practice against. Free to use, deterministic, with the kinds of edge cases agents encounter in production.</p>
<h2>What&#39;s in it</h2>
<p>Six endpoints, each chosen to force agents to handle something real-world.</p>
<h3><code>GET /agent/v1/users</code></h3>
<p>Cursor-paginated user list. No <code>?page=N</code>. Agents have to learn <code>meta.next_cursor</code> and pass it back unchanged. Limits over 100 are silently clamped, so agents have to verify <code>meta.returned</code> matches their requested limit. Sparse fieldsets via <code>?fields=id,email</code>.</p>
<pre><code class="language-bash">curl https://reqres.in/agent/v1/users?limit=2
</code></pre>
<p>Returns 247 users per seed (default <code>seed=42</code>), with nullable nested fields, ULID IDs (<code>usr_01H...</code>), and ISO 8601 timestamps with millisecond precision. The same request always returns the same response.</p>
<h3><code>GET /agent/v1/users/:id</code></h3>
<p>Deeply nested single resource with optional expansion. Without <code>?expand=</code>, nested resources return as references (<code>{id, object_type}</code>). With <code>?expand=addresses,activity,organizations</code>, they&#39;re inlined. Activity records have heterogeneous shapes -- a <code>login</code> event has <code>ip_address</code> and <code>user_agent</code>, a <code>profile_updated</code> event has <code>changed_fields[]</code> instead. Agents that assume uniform array members break.</p>
<h3><code>POST /agent/v1/auth/login</code></h3>
<p>Two response shapes depending on the email. Normal accounts return a session with token, refresh_token, expires_at, and user object. Accounts with email containing <code>+mfa@</code> return an MFA challenge with a <code>next_step</code> hypermedia hint pointing to the verification endpoint. Trains agents to handle response shape variation and to use hypermedia for recovery.</p>
<p>Other deterministic test triggers: <code>+wrong@</code> for invalid_credentials (401), <code>+locked@</code> for account_locked (401).</p>
<h3><code>GET /agent/v1/orders</code></h3>
<p>Relational data: orders reference users, products, addresses, and payment methods. Money is always <code>{amount, currency, formatted}</code> Stripe-style -- <code>amount</code> is in the smallest currency unit (cents for USD), never a decimal. Some line items reference deleted products, where <code>product.deleted_at</code> is set and <code>product.name</code>/<code>product.price</code> are <code>null</code>. Forces agents to handle the &quot;referenced resource was deleted after the parent was created&quot; case.</p>
<h3><code>GET /agent/v1/scenarios/:scenario</code></h3>
<p>Fifteen deliberate failure modes for testing error handling without trying to force errors on real endpoints:</p>
<ul>
<li><code>rate-limited</code>, <code>server-error</code>, <code>bad-gateway</code>, <code>timeout</code>, <code>validation-error</code></li>
<li><code>unauthorized</code>, <code>forbidden</code>, <code>not-found</code>, <code>conflict</code>, <code>too-large</code></li>
<li><code>slow</code>, <code>partial-content</code>, <code>redirect-loop</code>, <code>malformed-json</code>, <code>empty-response</code></li>
</ul>
<p>Every response includes the header <code>X-Agent-Sandbox-Intentional: &lt;scenario-name&gt;</code>. Configure your error reporter (Sentry, Bugsnag) to suppress responses with this header so your agent&#39;s training scenarios don&#39;t fill up your alert dashboard.</p>
<p><code>timeout</code> and <code>slow</code> are special: they return immediately with a <code>X-Agent-Sandbox-Simulated-Delay</code> header instead of actually holding the connection open for 30 or 10 seconds. Agents that want to test real timeout handling read the header and delay client-side. Holding open thousands of slow connections would have exhausted our origin&#39;s connection pool.</p>
<h3><code>GET /agent/v1/health</code></h3>
<p>Cheap to poll. Returns sandbox status, version, uptime, and the caller&#39;s current rate-limit status. Agents can probe this before a burst of requests to know how much quota they have left. Not edge-cached (<code>Cache-Control: no-store</code>) because the response varies by the caller&#39;s tier - the numbers you see are always yours.</p>
<h2>Why determinism matters</h2>
<p>Same <code>(seed, cursor, params)</code> always returns the same response. This is the single most important property of the sandbox.</p>
<p>Agents fail in production all the time. The hard part isn&#39;t fixing the failure -- it&#39;s reproducing it. With non-deterministic test data, an agent that worked in CI on Tuesday and broke on Wednesday is a haunted-house debugging session. With deterministic test data, you replay the exact same request and get the exact same response, every time. The failure is reproducible. The fix is testable.</p>
<p>This is the same reason Stripe&#39;s test mode is deterministic. It&#39;s the reason CI test fixtures are checked into version control. Determinism turns &quot;this is broken intermittently&quot; into &quot;here is the reproducer.&quot;</p>
<h2>Conventions</h2>
<p>We picked conventions agents will already be familiar with from working with Stripe, GitHub, and other production APIs:</p>
<ul>
<li><strong>IDs:</strong> ULID format with type prefix (<code>usr_</code>, <code>ord_</code>, <code>prd_</code>, <code>adr_</code>). 26 characters after the underscore. Lexicographically sortable.</li>
<li><strong>Timestamps:</strong> ISO 8601 with millisecond precision, always UTC. <code>.000Z</code> suffix even for whole-second values, for parse consistency.</li>
<li><strong>Money:</strong> Always an object <code>{amount: integer_in_smallest_unit, currency: &quot;ISO 4217 code&quot;, formatted: &quot;human-readable&quot;}</code>. Never a decimal number.</li>
<li><strong>Cursors:</strong> Opaque base64-encoded JSON with a nonce. Two requests at the same offset produce different cursor strings -- agents must treat cursors as opaque and pass them back unchanged.</li>
<li><strong>Cache-Control:</strong> Data endpoints <code>max-age=60, s-maxage=300</code>. Scenario endpoints <code>no-store</code>.</li>
<li><strong>Request IDs:</strong> Every response sets <code>X-Request-ID</code>. Include in support requests.</li>
</ul>
<p>Full conventions in <a href="/llm.txt"><code>/llm.txt</code></a> and the <a href="/openapi.json">OpenAPI spec</a>.</p>
<h2>Pricing</h2>
<p>The sandbox is <strong>free to use</strong> with IP-based rate limits - 100 requests/day per IP, no signup. Good for prototyping and first-integration smoke tests. Free tier also exposes 3 sample <code>/scenarios/*</code> (<code>rate-limited</code>, <code>validation-error</code>, <code>malformed-json</code>) so you can wire up error handling before committing.</p>
<p>For production volume, there&#39;s a new <strong>Agent Developer plan at $49/month</strong> that gives you 10 million requests per month (~333,333/day), access to all 15 failure scenarios, and a usage dashboard at <a href="https://app.reqres.in/agents">app.reqres.in/agents</a>. Subscribers also get Dev plan quotas on the main ReqRes BaaS product (collections, app users, request logs, custom endpoints).</p>
<p>Subscribing provisions an <code>x-agent-id</code> key (format: <code>agt_&lt;64 hex&gt;</code>) which you send on every call to raise the cap. The key is attached to your account in Stripe, not to an agent identity or version string - pass the same key from any agent or environment. Arbitrary strings in the header (e.g. <code>vendor/agent/version</code>) are rejected with 401.</p>
<h2>How agents discover the sandbox</h2>
<p>We publish three machine-readable manifests:</p>
<ul>
<li><code>/llms.txt</code> -- top-level discovery, ~50 lines, points to deeper references</li>
<li><code>/llm.txt</code> -- comprehensive text guide with every endpoint, error shape, and convention</li>
<li><code>/openapi.json</code> -- OpenAPI 3.0.3 spec, full schemas</li>
</ul>
<p>Point your agent at any of these. The intent is that an agent should be able to fetch one of them once, understand the entire API, and write working code without any human in the loop.</p>
<h2>What&#39;s next</h2>
<p>This is v1. Things we&#39;re explicitly NOT shipping in v1:</p>
<ul>
<li>Authentication on the agent endpoints (open for now, IP rate-limiting)</li>
<li>Write operations on <code>/agent/v1/users</code></li>
<li>Webhooks or long-polling</li>
<li>Time-series data endpoints</li>
<li>GraphQL variant</li>
<li>SDK on npm (<code>@reqresin/agent-sandbox</code> -- coming soon)</li>
</ul>
