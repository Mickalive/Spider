            <p>You can build a working app against ReqRes in minutes if you give your AI tool the right context. Without it, the LLM will guess at endpoints, invent auth headers, and generate code that looks right but fails on every request.</p>
<p>This guide covers what to include in your prompt, what mistakes LLMs make, and how to get from zero to a working app fast.</p>
<h2>The one thing LLMs get wrong</h2>
<p>Every LLM knows about reqres.in. It&#39;s in their training data. But they know the <strong>old</strong> ReqRes: the free demo API with <code>/api/users</code> and fixture data that doesn&#39;t persist.</p>
<p>The new ReqRes has persistent collections, real auth, and project-scoped API keys. When you say &quot;build an app against ReqRes,&quot; the LLM defaults to the demo endpoints. Your app will fetch fixture users and think it&#39;s working, but nothing will actually save.</p>
<p><strong>Fix:</strong> Tell the LLM which API surface you want. There are three:</p>
<ol>
<li><strong>Demo API</strong> (<code>/api/users</code>, <code>/api/login</code>) - Read-only fixtures, no auth needed, nothing persists</li>
<li><strong>Project API</strong> (<code>/api/collections/{slug}/records</code>) - Your data, your schema, full CRUD, persistent</li>
<li><strong>Agent Sandbox</strong> (<code>/agent/v1/users</code>, <code>/agent/v1/orders</code>, <code>/agent/v1/scenarios/*</code>) - Designed specifically for AI agents to practice against. Cursor pagination, deeply nested data, deterministic seeded fixtures, 15 deliberate failure modes. No auth, no setup. See <a href="https://reqres.in/for/ai-agents">/for/ai-agents</a> and <a href="https://reqres.in/llm.txt">/llm.txt</a>.</li>
</ol>
<h2>What to include in your prompt</h2>
<p>Here&#39;s the minimum context an LLM needs to generate working ReqRes code:</p>
<pre><code>I&#39;m building against ReqRes (reqres.in).

My API base URL: https://reqres.in
My project ID: [from your dashboard]
My manage key: pro_[your key] (server-side only, full CRUD)
My public key: pub_[your key] (browser-safe, read-only)

I have a &quot;products&quot; collection with this schema:
  - name: string
  - price: number
  - category: string
  - in_stock: boolean

Endpoints:
  GET    /api/collections/products/records?project_id=MY_ID
  POST   /api/collections/products/records?project_id=MY_ID
  PUT    /api/collections/products/records/{id}?project_id=MY_ID
  DELETE /api/collections/products/records/{id}?project_id=MY_ID

Auth: include x-api-key header on all requests.
Environment: include X-Reqres-Env: prod header.
POST/PUT body must be wrapped: {&quot;data&quot;: {&quot;name&quot;: &quot;...&quot;, &quot;price&quot;: 9.99}}

Full API reference: https://reqres.in/llm.txt
</code></pre>
<p>That&#39;s it. With this context, Claude Code, Cursor, or ChatGPT will generate correct requests on the first try.</p>
<h2>Common LLM mistakes and how to prevent them</h2>
<h3>1. Missing the <code>data</code> wrapper</h3>
<p>LLMs will generate:</p>
<pre><code class="language-json">{&quot;name&quot;: &quot;Product&quot;, &quot;price&quot;: 9.99}
</code></pre>
<p>The API expects:</p>
<pre><code class="language-json">{&quot;data&quot;: {&quot;name&quot;: &quot;Product&quot;, &quot;price&quot;: 9.99}}
</code></pre>
<p><strong>Fix:</strong> Include &quot;POST/PUT body must be wrapped in <code>{data: {...}}</code>&quot; in your prompt. Or point the LLM to <code>https://reqres.in/llm.txt</code> which documents this.</p>
<h3>2. Using the demo API instead of collections</h3>
<p>The LLM will default to <code>POST /api/users</code> (demo, doesn&#39;t persist) instead of <code>POST /api/collections/products/records</code> (project, persists).</p>
<p><strong>Fix:</strong> Be explicit: &quot;Use the project collections API, not the demo /api/users endpoints.&quot;</p>
<h3>3. Confusing the two key types</h3>
<p>LLMs will put your manage key (<code>pro_*</code>) in browser-side JavaScript. That key has write/delete permissions and should never be exposed to clients.</p>
<p><strong>Fix:</strong> Include both keys in your prompt with clear labels:</p>
<ul>
<li><code>pro_*</code> = server-side, curl, CI/CD, Node.js scripts</li>
<li><code>pub_*</code> = browser, React, client-side reads</li>
</ul>
<p>For browser writes, use App Users with session tokens instead.</p>
<h3>4. Forgetting the environment header</h3>
<p>Requests without <code>X-Reqres-Env: prod</code> may hit the wrong environment or fail.</p>
<p><strong>Fix:</strong> Include &quot;Add X-Reqres-Env: prod header&quot; in your prompt.</p>
<h3>5. Inventing emails for demo login</h3>
<p>The demo <code>/api/login</code> only accepts fixture emails (<a href="mailto:george.bluth@reqres.in">george.bluth@reqres.in</a>, <a href="mailto:eve.holt@reqres.in">eve.holt@reqres.in</a>, etc.). LLMs will generate <code>test@example.com</code> which returns 400.</p>
<p><strong>Fix:</strong> Include a few fixture emails in your prompt, or say &quot;Use <a href="mailto:eve.holt@reqres.in">eve.holt@reqres.in</a> for demo login.&quot;</p>
