## 2. State, action, target, unit of analysis

**State representation (raw -> derived, no BrowserGym required):**
- Raw (synthetic orthogonal+mixed): `url` string as observed, `method` (GET/POST), synthetic `headers_observed`/`body_observed` dicts (for mixed, both headers_observed and body_observed and url_query contain aliased keys simultaneously within one request). Plus `intent` string (goal).
- Derived for retrieval/mining and for rewriting/invocation: `url_path` (split `/`), `url_query` dict (parse `?k=v`), `url_segments` list, `header_keys_observed` (lowercased keys from headers_observed), `body_json_keys` (parsed JSON keys if applicable), serialized query string `intent + ' ' + url_path + ' ' + query_keys + ' ' + header_keys + ' ' + body_keys + ' ' + method` for centroid scoring. Losses disclosed: visual layout pixels, timing, auth token values beyond key presence, AX tree — bounded to tested header/body/auth aliasing + mixed.
- Hierarchical component representation: For each mechanism episode, parse `action_template` string to extract semantic components: `url_segments` (non-slot path tokens), `query_keys` (keys before `=` or `${slot}`), `header_keys` (e.g., `ApiKey`, `X-Reset-Token`), `body_fields` (JSON keys), `auth_scopes` (permission values). Extract via regex `\$\{[^}]+\}` for slots and string splitting, no hidden_expected access. Components are sets; themes are clusters of episodes by Jaccard(component_set_i, component_set_j) >=0.6.
- WebAPI endpoint representation: For each endpoint spec (method + path_template + header_template + body_template + auth_scope), parse similarly to extract endpoint components: `path_segments`, `query_keys`, `header_keys`, `body_fields`, `auth_scopes`, `method`. Endpoint themes are clusters of endpoint specs by Jaccard(endpoint_component_set_i, endpoint_component_set_j) >=0.6. AX fields None for synthetic; no 1280x720 viewport needed per Director rationale.
- Forbidden: `alias_family`, `query_key`, `target_prefix`, `routing_prefix`, `target_style`, `path_style`, `header_key`, `body_field`, `auth_scope`, `expected_template`, `expected_endpoint`, `resource` answer labels are NOT in derived_context nor in component/endpoint extraction; stored only as hidden `expected` metadata for scoring. Audit verifies no forbidden reads via harness `hierarchical_retrieve`/`flat_retrieve`/`webapi_mine` signatures and index manifest audit. Correct-family rule derives family solely from template-parsed candidate family and derived_context observed family overlap, never from hidden_expected_family.
- Correct-family derivation: `candidate_families` = set of families present as slot types in candidate template/endpoint (header if template contains header slot, body if body JSON slot, auth if auth scope slot, query if query slot, path if path segment slot). `observed_families` = set of families present in derived_context (header if headers_observed non-empty aliased key, body if body_observed non-empty, auth if auth scope observed, query if url_query non-empty, path if url_segments contains alias token). Cross-family check = intersection non-empty. This is auditable via template parsing logs.

**Action/endpoint representation and two frozen binding rules:**
- Mechanism `action_template` is URL/header/body/auth template strings with `${slot}` and for mixed tasks simultaneously header+body+query slots. Endpoint spec is tuple (method, path_template, header_template, body_template, auth_scope) with same slot syntax. Binding via deterministic `kernel._bind` plus header/body field substitution.
- RULE-VERBATIM: No rewriting. Candidate template/endpoint bound verbatim via _bind; if required slot not provided in derived_context, bind fails -> false_accept or UNKNOWN per confidence gate. This is the manipulation check that should collapse alias-OOD to 0/40.
- RULE-CORRECTFAMILY (correct-family-required): For each candidate, compute candidate_families and observed_families as above. Candidate eligible only if intersection non-empty. If eligible, rewrite only the overlapping family slots with observed values sorted alphabetically, one adoption per family, cross-family slots left unfilled (so bind fails if still missing). Cross-family adoption is forbidden: a body field placeholder cannot be filled with a header observed key, nor header placeholder with body key. Mixed tasks require all channels' families to be jointly covered by the candidate set's rewritten candidates? Per-task correct only if ALL channels (header + body + query + method) jointly correctly rewritten/invoked after correct-family rewrite (partial = false_accept). This isolates retrieval effect: any correct_resolution improvement under correct-family rule is attributable to retrieving correct family, not to stronger rewriting, since rewriting is held constant and forbidden to invent cross-family keys.
- Confidence for both rules = softmax over candidate scores (temp 0.15) + deterministic jitter gated UNKNOWN<0.80 for ECE. All endpoint indexing fit on train registry only; no hidden_expected access.
- Harness exposes `hierarchical_retrieve(intent, derived_context, registry) -> candidates`, `flat_retrieve(intent, derived_context, registry) -> candidates`, `webapi_mine(intent, derived_context, endpoint_catalog) -> endpoint_candidates`, and `bind_verbatim` / `bind_correct_family` wrappers for audit.

**Target (primary measurand):**
- Per-task outcome in `{correct_resolution, correct_endpoint_invocation, false_accept, UNKNOWN}` (mutually exclusive per pipeline per rule, sum to 1 per stratum).
  - Under RULE-VERBATIM: `correct_resolution` (template pipelines) = retrieved set contains verbatim-correct template and bind yields `expected_bound` (hidden_expected_template bound equality including header/body field equality and for mixed all channels jointly correct). Expected 0/40 for alias-OOD since test form not in registry. `correct_endpoint_invocation` (WebAPI) analogously 0/40 expected.
  - Under RULE-CORRECTFAMILY: `correct_resolution` = retrieved set contains candidate whose family matches observed family and after correct-family-restricted rewrite, `bound_action` equals `expected_bound` (including header/body field equality and for mixed all channels jointly correct). `correct_endpoint_invocation` = mined endpoint candidate set contains endpoint that after correct-family-restricted deterministic binding yields `expected_endpoint_bound` (method+path+header+body+auth jointly correct).
  - `false_accept` = resolved/invoked to wrong template/endpoint or bound incorrectly or should have abstained.
  - `UNKNOWN` = correctly abstains when no applicable mechanism/endpoint or gated confidence<0.80.
- Retrieval/endpoint measurands per task under correct-family rule:
  - `recall@k` = 1 if candidate set contains at least one mechanism/endpoint whose template after correct-family-restricted rewriting yields correct bound, else 0. Coverage = mean recall@k over pooled alias-OOD.
  - `distinct_components` = number of distinct semantic/endpoint component types (header vs body vs auth vs path segments) represented in candidate set; density = distinct_components / k.
  - Coverage gain = hierarchical-CF coverage - best flat-CF coverage (max of TFIDF-K5-CF and EMBED-K5-CF) and WebAPI-CF coverage - best flat-CF coverage reported separately. Evidence density gain = WebAPI-CF density - best flat-CF density and hierarchical-CF density - flat-CF density.
- Secondary: calibration — `ECE` over 5 confidence bins (candidate-relevance-derived confidence) plus abstention precision/recall; per-family (header/body/auth) and held-out-9 and mixed-10 breakdowns; adaptive k distribution; endpoint theme count; verbatim collapse magnitude (delta 0.975 -> 0.0).
- Mixed multi-channel target: correct only if ALL channels (header + body + query + method) jointly correctly rewritten/invoked; partial counts as false_accept.

**Unit of analysis:** Single `retrieve(k) + bind_rule + verify` or `mine(k) + endpoint_invoke_rule + verify` call per task per rule. Paired design: each task evaluated under each pipeline under each rule (within-task). Resampling unit is task family (block bootstrap over tasks grouped by family header/body/auth/mixed to respect trajectory-grouped structure per Director question).
